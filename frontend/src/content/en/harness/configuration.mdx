# Configuration

<Callout type="info" emoji="⚙️">
  Infrastructure behavior is driven by <code>config.yaml</code>. Model
  definitions are managed separately by platform administrators in
  <strong>Admin → System Settings → Models</strong> and stored in PostgreSQL.
</Callout>

ActWeave explicitly separates infrastructure process configuration from
database-governed settings, keeping deployments reproducible, auditable, and
easy to customize per environment.

## Config file location

ActWeave resolves `config.yaml` using the following priority order:

1. The path passed to `AppConfig.from_file(config_path)` explicitly.
2. The `DEER_FLOW_CONFIG_PATH` environment variable.
3. `config.yaml` in the repository root.

If none of these paths exist, the application raises an error at startup.

To use a custom location:

```bash
export DEER_FLOW_CONFIG_PATH=/path/to/my-config.yaml
```

## Environment variable interpolation

Any field value can reference an environment variable using `$VAR_NAME` syntax:

```yaml
database:
  url: $DATABASE_URL
```

This keeps secrets out of the config file itself. The variable is resolved at runtime from the process environment.

## The `use` field

Many configuration entries use a `use:` field to specify the Python class or object to instantiate. The format is:

```
package.subpackage.module:ClassName
```

or for module-level objects:

```
package.subpackage.module:variable_name
```

Examples:

```yaml
sandbox:
  use: deerflow.sandbox.local:LocalSandboxProvider

tools:
  - use: deerflow.community.tavily.tools:web_search_tool
    api_key: $TAVILY_API_KEY
```

This pattern is how ActWeave achieves pluggability without hardcoding class references.

## Model provider settings

Platform administrators configure provider adapters, provider model names,
capabilities, and bounded provider-specific JSON in **Admin → System Settings
→ Models**. API keys are selected through versioned System Credentials; they
are never stored in model settings or `config.yaml`.

Each Run freezes the exact model configuration and Credential version admitted
for that Run, so later administrative changes do not silently alter queued
work.

## Configuration version

`config.yaml` includes a `config_version` field that tracks the schema version:

```yaml
config_version: 33
```

When the schema changes (new fields, renamed sections), this number is bumped. If your local `config.yaml` is behind the current version, run:

```bash
make config-upgrade
```

This merges new fields from `config.example.yaml` into your existing `config.yaml` without overwriting your customizations.

## Minimal config to get started

The minimum valid `config.yaml` requires a PostgreSQL connection and a sandbox.
At least one active database-backed model must also be configured through the
admin UI before conversations can run:

```yaml
config_version: 33

database:
  url: $DATABASE_URL

sandbox:
  use: deerflow.sandbox.local:LocalSandboxProvider

tools:
  - use: deerflow.community.ddg_search.tools:web_search_tool
  - use: deerflow.community.jina_ai.tools:web_fetch_tool
  - use: deerflow.sandbox.tools:ls_tool
  - use: deerflow.sandbox.tools:read_file_tool
  - use: deerflow.sandbox.tools:write_file_tool
  - use: deerflow.sandbox.tools:bash_tool
```

Start from `config.example.yaml` in the repository root and uncomment the sections you need.
