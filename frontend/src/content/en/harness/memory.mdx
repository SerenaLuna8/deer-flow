# Memory

Project Memory is one private, versioned Markdown document for each authenticated owner in a project. PostgreSQL stores the current document, pending history entries, Dream runs, immutable document versions, and the exact document snapshot frozen for each admitted Run. The server derives project, owner, and the fixed internal namespace from the authenticated request; the browser cannot select another scope.

Thread summaries remain separate. They compact one Thread's model context and are preserved when long-term Memory is reset.

## Document section template

A platform administrator maintains two to eight ordered plain titles under
**Admin → System settings → Memory**. The template is an independently versioned and audited
PostgreSQL `memory_document` system policy, not a `config.yaml` setting. When a project/owner
scope creates its Memory document for the first time, the server freezes those sections and the
exact policy version on the document row; Run Memory snapshots freeze the same section contract.
Later template changes affect only new documents. They never reorder existing documents, rewrite
historical versions, or cancel in-flight Dreams.

## SNIP and pending history

When a Thread is compacted, SNIP makes one bounded model call over complete older turns. Its validated tagged output becomes both the Thread's `summary_text` and a pending private history entry. An exact `(nothing)` still updates the Thread summary but creates no long-term entry. The checkpoint receipt and database transaction use an idempotent handshake so a retry cannot archive the same compaction twice.

Use `/compact` to run only this Thread-local compaction. The full visible chat remains available.

## Dream

Dream periodically organizes at most the oldest 20 pending entries into the current document. The isolated Dream session receives only the current document, the bounded pending batch, and in-memory read/replace tools. It has no shared Agent, files, shell, web, MCP, Skill, or Subagent access.

Document replacement, a new immutable version, a real unified diff, cursor advancement, pending-entry tombstones, and Job success settle atomically. If model, tool, validation, timeout, or database work fails, the document and pending entries remain unchanged for a safe retry.

`/Dream` first compacts the current Thread and then admits one manual Dream batch. The Memory page's **Organize now** action admits the same job without changing chat messages.

## Recall

Run admission reads the current bounded document and its section contract once, then freezes both in a single Run snapshot. Worker model boundaries reuse only that snapshot; first recall performs no model call, vector lookup, or ranking query. A Dream finishing during a Run, or an administrator changing the section template, cannot change that Run's Memory.

When enabled, the complete frozen document is injected as a hidden, low-authority Human message marked as private data rather than an instruction. Turning Memory off skips injection at the next model boundary. Reset removes long-term documents, history, versions, Dream records, and Run Memory snapshots while preserving chats and Thread summaries.

## Project Memory page

The project page shows only:

- the current long-term document, version, update time, and pending count;
- **Organize now** and an active-Dream state;
- Dream and restore history with the processed count and real diff;
- each saved document version and an explicit restore confirmation.

Restore writes the selected historical content as a new version. It never rewinds the history cursor or deletes later records. `/dream-log [version]` opens this history, and `/dream-restore <version>` asks for confirmation before calling the restore API. None of these commands is sent to the normal Agent chat flow.

Runs without a trusted project-private scope cannot read, inject, organize, restore, or reset Memory.
