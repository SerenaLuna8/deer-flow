# Deployment Guide

The Fluva topology consists of Nginx, Frontend, Gateway, Worker, an optional Scheduler, and an optional Sandbox Provisioner. PostgreSQL is the only application persistence database and must be provisioned explicitly.

<Callout type="warning">
  The repository supports host-process application startup. Browsers, model providers, and Sandbox modes require separate capacity, security, and failure validation in the target environment. This page is not production certification.
</Callout>

## Prepare the deployment

1. Generate and validate the repository-root `config.yaml`.
2. Inject model, authentication, and database secrets through `.env` or the process supervisor's secret store. Never commit them.
3. Pre-create a non-superuser application role.
4. Explicitly initialize a fresh PostgreSQL target:

```bash
export POSTGRES_ADMIN_URL='<administrator URL for the postgres maintenance database>'
export DATABASE_URL='<fresh Fluva target database URL>'
make setup-db
make check-db
```

Runtime processes only validate the target; they never create a database or
repair or upgrade its schema. Use `make setup-db` for a fresh target; future
known predecessors are upgraded only with an explicit `make upgrade-db` during
a stopped-service, backed-up maintenance window.

## Local full stack

```bash
make dev       # hot reload
make start     # optimized local build
make stop
```

The unified entry point is `http://localhost:2026`. Local logs are under `logs/{gateway,worker,scheduler,frontend,nginx}.log`, and local runtime state defaults to `backend/.fluva-flow`.

Before deployment, verify at least the following:

- Expose only Nginx `2026`; keep Gateway `8001`, Frontend `3000`, and Provisioner `8002` internal.
- Configure TLS, network access control, strong authentication secrets, and a secret manager.
- Gateway, Worker, and Scheduler use the same canonical `config.yaml` and `DATABASE_URL`.
- Worker readiness, Scheduler ownership, durable stream reconnect, and project isolation pass in the target environment.
- `backend/.fluva-flow` contains local runtime files/Sandbox projections only; it is not the authority for project business data or the asset catalog.

## Sandbox selection

| Mode | Boundary |
| --- | --- |
| `LocalSandboxProvider` | Commands execute in the host environment; trusted local tasks only |
| Container/AIO provider | Container isolation; validate Docker socket, network, and mount permissions |
| Provisioner/Kubernetes | A separate service creates Sandbox Pods; requires cluster-level security validation |

Provisioner/Kubernetes is a Sandbox provider only; this repository does not provide a Kubernetes/Helm deployment target for the complete Fluva stack.

Docker is optional and is supported only as an AIO Sandbox runtime. Use `make setup-sandbox` to prepare its image. The standalone Kubernetes control service lives under `sandbox/provisioner/`.

Sandbox isolation does not replace project authorization, least-privilege secret injection, or network egress control.

## Verify

```bash
make check-db
curl http://localhost:2026/health
make doctor
```

After login, inspect Worker, Scheduler, stream, quota, and audit readiness under `/admin/operations`, then exercise a real project-scoped Run and SSE reconnect.

See [Operations & Troubleshooting](/docs/application/operations-and-troubleshooting) for diagnostics.
