# Agents and Threads

ActWeave App supports multiple named agents and maintains conversation state across sessions through threads and checkpointing.

## Agents

### Main and the project default

Main is the project-level orchestrator and the fallback when the project has no custom default Agent. For each Run, the server resolves all effective System assets plus all active, published Agent, Skill, and MCP assets owned by the entered project, then freezes their exact versions in the Run snapshot. Main can delegate to the other admitted Agents, but it never sees assets owned by another project. It does not require a project Agent binding, and the browser does not enable dependencies on its behalf.

A project administrator may instead select an active, published project Agent as the project default. A configured default that is no longer executable fails closed; ActWeave does not silently switch it back to Main.

The current project default Agent can be deleted directly. Deletion soft-archives it, clears the default automatically, and makes subsequent project work fall back to Main. Existing conversations, Automations, Channels, OAuth connections, and Run records are retained rather than cascade-deleted. An already admitted Run continues with its frozen snapshot; starting a new Run from an existing conversation reports that the Agent was deleted and requires switching Agents. An archived record no longer occupies the project name, so the same slug may be reused by a new Agent with a new ID; old conversations remain bound to the archived ID.

### Custom agents

Custom agents are named variants of the Lead Agent. Each one can have:

- a **display name** and an auto-derived ASCII slug (the `name` used internally)
- a specific **model** to use by default
- exact published **Skill and MCP versions**
- a restricted set of **tool groups**
- a custom **system prompt** or agent-specific instructions

Agents are created and managed from the entered project's **Agents** page. Platform administrators manage system agents under **Admin > Assets > Agents**. The corresponding authenticated APIs are scoped to that project or to the system-admin asset surface; there is no global workspace Agent client.

The slug is derived from the display name and must be unique among non-deleted Agents within its asset scope. After an Agent is archived, its slug can be reused by a new Agent with a new ID. Published versions and explicit project bindings are stored in PostgreSQL. Unlike Main, a custom Agent loads only the Skill and MCP versions referenced by that Agent version. Omitting a dependency does not inherit every project asset.

To create an Agent in the app, open **Agents**, choose **New Agent**, enter a name and brief, and answer the AI Builder's clarification questions. Review the generated Blueprint, assumptions, and conflicts before confirming. Error-severity conflicts block creation until another AI turn regenerates the candidate; editing a document alone does not resolve them. You may edit the four instruction documents or rename the Agent in the same session, including after a name conflict, without discarding the conversation. Builder creation automatically binds enabled System Skill/MCP dependencies; select exact project-authored Skill/MCP versions later from the Agent detail page.

Creating an Agent produces a suspended asset and Draft v1. Authors with `shared_assets.edit` may create new drafts by editing instructions or capability bindings, or by restoring a historical version; none of those actions changes the running version. A project publisher with `shared_assets.manage_bindings` must explicitly publish a selected draft and may then activate the Agent. Publishing and activation are separate CAS-protected operations.

If a session owner later retains only `shared_assets.read`, the saved Builder session remains available read-only, but it cannot be continued, edited, cancelled, or committed. In Builder review, the normalized name becomes both the new Agent's display name and slug; the general API still accepts `display_name` and `slug` separately.
Each user may retain up to eight incomplete design sessions in a project. Resume or cancel an existing design before starting another after that limit is reached.

The project API accepts only a complete definition at `POST /api/projects/{project_id}/agents`: `slug`, `display_name`, `description`, `agents_instructions`, `soul`, `identity`, `user_context`, `model_ref`, `model_settings`, `tool_groups`, `skill_version_ids`, and `mcp_version_ids`. The response contains both the suspended Agent asset and Draft v1; a name-only shell is rejected. Publish a reviewed draft with `POST /api/projects/{project_id}/agents/{agent_id}/versions/{version_id}/publish` and the current `expected_asset_version`. The project-admin override API follows the same definition and author/publisher contract.

### Restricting agent capabilities

To restrict a custom agent to specific skills:

```yaml
# agents/my-researcher/config.yaml
name: my-researcher
display_name: My Researcher
skills:
  - deep-research
  - academic-paper-review
# Set skills: [] to disable all skills for this agent
```

To restrict to specific tool groups:

```yaml
tool_groups:
  - research # only tools in the 'research' group are available
```

## Threads

A **thread** is a persistent conversation session. Each thread has:

- a unique thread ID
- a message history
- accumulated artifacts (output files)
- a title (auto-generated after the first exchange)
- a reference to the agent used

Threads are listed under the entered project's **Chats** page. Clicking a thread resumes that owner-scoped conversation.

### Thread lifecycle

<Steps>

#### Create

A new thread is created when you start a conversation. The thread ID is generated and the initial configuration (model, agent, skills) is recorded.

The composer follows that Thread's Agent: Main suggests every effective Skill in the current project, while a custom Agent suggests only the Skills referenced by its selected version. Historical `/skill` messages remain readable even if the current Agent or catalog later changes.

#### Run

Each user message triggers an agent run. The run streams tokens and tool calls back to the browser in real time. The thread state (messages, artifacts) is updated after each turn.

If the project Agent is suspended, the existing thread history remains readable, but sending, retry/regenerate, edited rerun, and human-input submission are disabled. Reactivate that Agent or start a new thread with another Agent.

#### Checkpoint

The project-scoped PostgreSQL checkpointer stores thread state after each turn, so the conversation survives process restarts.

#### Resume

Opening a thread from the sidebar loads its full history from persisted state. The agent picks up from where it left off.

</Steps>

### Thread persistence configuration

PostgreSQL is required for thread state and application data. Configure the shared connection through `database.url`:

```yaml
database:
  url: $DATABASE_URL
```

PostgreSQL drivers are default dependencies. A standalone `checkpointer` configuration is not accepted.

### Thread data storage

When you select, paste, or drop an attachment into a persisted thread, ActWeave
starts uploading it in the background while you continue typing. Sending waits
only for any unfinished portion and reuses the ready upload; it does not upload
the same attachment a second time.

Working files produced during a thread (uploads, intermediate files, output artifacts) are stored under:

```
backend/.deer-flow/threads/{thread_id}/user-data/
```

This directory is mounted into the sandbox as `/mnt/user-data/` for the agent to read and write.

In local and Docker development, this path may be mounted into the configured Sandbox. It contains working-file projections only; Thread metadata, messages, Run state, and asset authority remain in PostgreSQL.
