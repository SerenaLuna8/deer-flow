# Own secret material within consuming configurations

ActWeave stores each Configuration Secret within the model, Skill, MCP, or Channel configuration that consumes it instead of governing secrets as independently reusable assets. A secret used by multiple configurations is stored as a separate protected copy for each owner, and existing centrally managed secret data is not migrated. This removes cross-domain lifecycle and selection coupling at the cost of repeated entry and independent replacement, while retaining shared, business-neutral encryption, key loading, redaction, and execution-boundary injection infrastructure.

The Credential business asset is deleted in full: its catalog, pages, APIs, services, repositories, domain models, versions, grants, authorization capability, tables, migration utilities, operator tooling, documentation, and module-specific tests do not remain as compatibility surfaces. Configuration Secret Generations and Secret Tombstones live only in their consuming domains; no neutral shared layer may recreate a central secret catalog or lifecycle. Consumer security tests are rewritten under their owning domains rather than discarded.

## Domain ownership

- Each stable System Model configuration owns one opaque API Key through a Model-owned secret-generation table. Schema V1 removes `system_model_config_versions`; provider, model, settings, capability, and checksum fields live on the stable mutable Model configuration. Model configurations expose no version history and no version number. Reusing one physical Key across three model configurations produces three independent encrypted copies.
- Project and Project-bound System Skill secrets belong to the Project and exact Skill Version, with owner identity `project_id + Skill identity + skill_version_id + secret_name`. Each Skill declaration owns the target Sandbox environment-variable name, while its Project binding owns only the protected value. System Skill definitions declare required names and targets but never store values. Saving a forward Candidate decrypts and re-encrypts still-compatible values as independent Candidate-owned copies only when the actor has both `shared_assets.edit` and `shared_assets.manage_bindings`; otherwise the Candidate is saved unready. Added or changed declarations always require new input. Copying does not expose plaintext outside its authorized server-side re-encryption boundary and is serialized against replacement and clearing of the source value.
- Project and Project-bound System MCP secrets belong to the Project and exact MCP Version and slot, with owner identity `project_id + MCP identity + mcp_version_id + slot_id`. System MCP definitions declare slots but never store values. Project remote MCP remains limited to header and query authentication; one Project slot may declare either or both sinks and replaces their values atomically. System stdio MCP uses environment injection, and System remote MCP supports header, query, and its governed OAuth contract. A new Project MCP Version receives independently re-encrypted copies only when transport, effective origin, and slot schema are unchanged and the actor also has `shared_assets.manage_bindings`; otherwise it is unready until values are entered again.
- Project Channel secrets belong to the exact Project Channel Instance as one provider-specific bundle.
- Account passwords, JWT and CSRF material, database and Provisioner process secrets, and personal Channel OAuth tokens remain in their existing dedicated domains.

System definitions and Project bindings retain separate authority. Model secret management stays within existing System model administration; Project Skill/MCP and Project-bound System Skill/MCP values require `shared_assets.manage_bindings`; their definitions continue to require `shared_assets.edit`; Channel values require `project.channels.manage`. The shared `mcp.credentials.approve` capability and all Credential grants are removed.

Secret materialization is allowlisted by the consuming definition. Worker injects a Skill value only into its declared Sandbox environment target; a Sandbox cannot read or inherit arbitrary Worker or host environment variables. A System stdio MCP slot declares an exact child-process environment target, and the child receives a constructed environment rather than arbitrary host inheritance. Remote MCP slots declare an exact header, query, or governed OAuth sink. Project MCP remains remote-only and gains neither stdio nor environment-variable injection. No caller may supply an undeclared sink or request an arbitrary host environment variable.

Each consuming domain emits its own generic audit events for secret configuration, replacement, clearing, compatible copy, readiness transition, and definition-driven invalidation. Events contain only actor, owner and exact Version or slot identity, Generation identity, revision, result, and secret-free reason metadata. They contain no plaintext, ciphertext, transient input, or deterministic digest that could be compared against guessed plaintext. Credential-specific audit actions, enums, pages, and compatibility event types are deleted.

## Writes and readiness

Secret writes are write-only. Creating a Secret Generation requires a non-empty value, although its owning configuration may be created unready without one. An empty edit preserves the current value; replacement explicitly writes a new value; clearing requires separate confirmation. For secret material, public APIs expose only per-slot `configured` status, aggregate Secret Readiness, and revision metadata alongside the owning configuration's normal non-secret fields. Plaintext never enters API responses, browser storage, TanStack Query state, logs, snapshots, or diagnostic bundles, and browser controls are cleared immediately after submission.

Empty-input preservation is allowed only while the secret recipient identity remains unchanged. Changing a Model adapter or effective API origin, an MCP transport or sink, or a Channel provider or public application identity requires either a newly entered secret or separately confirmed clearing; the old value is never sent silently to the new recipient.

Secret replacement and clearing are last-write-wins operations. The last secret write to commit successfully becomes the Current Secret Generation. A revision is still incremented and returned as status metadata, but the write does not require an expected revision. Non-secret configuration edits may retain their existing optimistic concurrency contract.

Copying, replacement, clearing, and definition-driven invalidation lock the exact owner and source Generation needed by the transaction. A Skill or MCP copy can commit only from the Generation and compatible definition it validated. A changed System MCP definition serializes against all affected Project binding writes so that a concurrent write against the old definition cannot restore readiness. Discovery results carry both exact Version and Generation identity and are accepted only while both are still authoritative. These locks preserve commit-order last-write-wins semantics without adding Run scanning or cancellation.

Replacement and clearing operate at domain-safe granularity: one whole Model API Key, one Skill `secret_name`, one complete MCP slot payload, or one complete Channel provider bundle. Clearing a required value changes only Secret Readiness. It does not change a Model's active/default assignment, a Skill or MCP Current Version, or a Channel Instance's enabled state and bindings, and it never causes an implicit fallback. Later Runs that require an unready configuration are not admissible.

Model connection testing always requires a transient API Key supplied for that individual request. It never falls back to or decrypts the saved Key, never persists the transient value, and cannot run when the test field is empty.

Fresh setup creates three active `patched_deepseek` configurations against `https://api.deepseek.com`: `deepseek-v4-flash` and `deepseek-v4-pro` support thinking and reasoning effort, while `deepseek-v4-flash-vision-exp` additionally supports vision. Flash is the default System Model and the vision model is the default Vision Bridge selection. Setup reads one DeepSeek API Key from `ACT_WEAVE_BOOTSTRAP_DEEPSEEK_API_KEY` and encrypts it independently into three Model-owned Secret Generations with separate nonces. The plaintext value is never embedded in source, documentation, migrations, fixtures, or command output.

`make setup-db` never calls DeepSeek or any other external model Provider and does not treat Provider availability as a schema-installation dependency. It only preflights the required environment values, encrypts the bootstrap Key locally, and writes the resulting Model configurations and independent Secret Generations transactionally. Provider usability remains an explicit model-administration connection test that requires a transient Key for that request and cannot read a saved Key.

Replacing an MCP secret marks its discovery state stale, makes the MCP temporarily unready, and automatically schedules discovery with the new Generation. Only a discovery result for the still-current Generation may restore readiness; an older concurrent result is discarded. New Runs that depend on it fail normal readiness admission until discovery succeeds. Clearing leaves discovery stale and the MCP unready. Discovery does not cancel, modify, rebind, or retry already admitted Runs.

System remote MCP OAuth in Schema V1 supports only `client_credentials`. The System MCP Version owns the non-secret token endpoint, grant, scope, audience, response parsing, refresh skew, and allowlisted extra parameters. Each Project binding owns its own `client_id` and encrypted `client_secret` as one Project-shared service identity. Access tokens, token types, expiry, Authorization headers, locks, and caches exist only in Worker memory and are never persisted or returned.

Any changed System MCP v1 definition checksum immediately destroys every Project binding's secret ciphertext and leaves those bindings unready. Project values must be entered again even when a reviewer believes the new definition is compatible. Idempotent installation of an identical definition preserves bindings.

System Skill v1 is immutable after first installation. An identical checksum is an idempotent installation; any changed checksum is rejected before Project bindings or secrets are touched. A changed System Skill must be introduced under a new System Skill identity and receives no Project secret values automatically.

Moving a Project Skill Version to Historical or publishing a later MCP Version is not an implicit secret replacement or clearing. That lifecycle transition alone does not destroy the Version's independently encrypted Current Secret Generations. In particular, a superseded but still-published MCP Version may remain the exact dependency of an Agent and may supply its own secret to a later new Run. Retained Versions remain independently addressable for write-only status and explicit clearing; a superseded MCP Version also permits replacement and reruns discovery for that exact Version, while a Historical Skill permits clearing for explicit revocation but cannot receive a replacement that no future Run could resolve. Replacement and clearing destroy only the previous Generation of the same exact Version and slot; they never sweep independent copies owned by other Versions.

Physical Asset deletion retains its existing exact-reference gate: it is rejected while an Agent or retained Run Snapshot still requires the exact definition. A successful hard delete removes that Asset's domain-owned Secret Generations and Tombstones in the same transaction. Final Project purge is different because it first deletes the Project's retained Run references and then cascades through its domain-owned secrets and Assets.

## Run boundary

Run Admission pins exact Model, Skill, and MCP Configuration Secret Generation references and integrity digests without copying plaintext or ciphertext into the Run Snapshot. An admission whose authoritative secret resolution begins after a secret-write commit must resolve that write's final value. Admissions overlapping the write receive no ordering guarantee and are treated like existing Runs.

Because System Model configurations are mutable and unversioned, Run Admission copies their complete secret-free provider payload and checksum into the Run Snapshot. Memory Dream admission freezes the same payload and the exact matching Model Secret Generation reference and integrity digest in its own execution snapshot. Existing Runs, Job retries, and queued Memory Dreams therefore keep their admitted model definition and secret reference without creating or retaining a Model Version business object. A later secret replacement destroys the old Generation exactly as it does for a Run: it does not rebind, cancel, or otherwise modify an admitted Memory Dream, and later materialization of the destroyed Generation fails closed.

Every other durable record that previously referenced a System Model Version keeps only the provenance it actually needs: a stable Model configuration identity plus copied checksum and execution-snapshot provenance, or a direct reference to the owning execution snapshot. No history, Memory, builder, or audit table may recreate a Model Version business object or depend on the mutable current Model row as proof of an earlier exact payload.

Any other admitted or persisted model execution profile, including Agent and Skill design generation, follows the same rule as a Run or Memory Dream: it freezes the complete secret-free Model payload and checksum together with the exact matching Model Secret Generation reference and integrity digest. Later Model edits or secret writes do not rebind, cancel, or rewrite that execution profile.

Replacement and clearing never scan, interrupt, cancel, revoke, or rebind an admitted, preparing, or running Run. Its Worker attempts use the fixed snapshot and may succeed or fail according to materialization timing and the external system; ActWeave adds no special recovery logic. A user regeneration or restored-input submission creates a new Run and resolves the then-current configuration, while an automatic Job retry remains part of its original Run.

When replacement or clearing commits, the authoritative domain transaction removes the previous Generation's ciphertext immediately without waiting for referencing Runs. Its Secret Tombstone retains identity and closure-integrity metadata that cannot serve as a plaintext-secret fingerprint. After commit, no application resolution path can retrieve the old ciphertext. PostgreSQL MVCC pages, WAL, replicas, storage snapshots, and backups follow their own infrastructure retention and destruction policies; this design does not claim instantaneous physical erasure from those media. A Run that already materialized the value may continue, while any later materialization of that old Generation fails closed.

OAuth access-token caches, Model clients, MCP discovery state, and Channel clients are keyed by exact recipient and Secret Generation or verify that Generation immediately before reuse. A new admission or delivery after a secret-write commit cannot accidentally reuse a cached value from the previous Generation. An already admitted Run that still has an old value materialized in its isolated execution state may continue, as allowed above.

Channel secrets are deliberately excluded from this snapshot rule. Inbound authority pins the Channel Instance, while outbound delivery uses that instance's current enabled and ready configuration. A replacement can therefore make an in-flight Run reply with the new Channel bundle, and clearing can make its delivery fail.

Entering Project `pending_deletion` is not itself an implicit secret clearing. During the existing 30-day recovery window, Project-owned Configuration Secret ciphertext and Secret Tombstones otherwise remain intact so that restoring the Project does not require values to be entered again. This retention rule does not undo or override a replacement, clearing, or changed-System-MCP invalidation that commits separately under its normal authority. The final irreversible Project purge deletes every Project-owned Configuration Secret Generation and Tombstone through its consuming domain's cascade. It does not delete System Model secrets or definition-level state that is not owned by that Project.

## Encryption and configuration

Schema V1 uses AES-256-GCM envelopes with a fresh random nonce, recipient-bound additional authenticated data, and one Base64-encoded 32-byte key loaded from `ACT_WEAVE_SECRET_KEY`. It has no key identifier, keyring document, rotation operation, or historical master keys. Gateway and Worker validate this setting at process startup. Only first installation into an empty database persists the three bootstrap Model secrets, so only that path preflights both `ACT_WEAVE_SECRET_KEY` and `ACT_WEAVE_BOOTSTRAP_DEEPSEEK_API_KEY` before executing database DDL. Missing or invalid Base64, a decoded master key other than exactly 32 bytes, or an empty bootstrap Key aborts without creating the schema. After successful installation the bootstrap Key may be removed; running `make setup-db` against the correct existing Schema V1 performs read-only validation without requiring the bootstrap Key and never rewrites the Model configurations. Losing or changing the runtime master key makes existing Configuration Secrets unreadable and requires their values to be entered again.

All repository environment variables use the `ACT_WEAVE_` prefix, including authentication, audit, Sandbox, path, and internal-service configuration. No compatibility aliases remain. Python package names and non-environment protocol fields are outside this environment-variable naming contract.

## Schema baseline

This is a development-stage baseline replacement rather than an upgrade. The existing migration chain and all current database contents, including Runs, approvals, and audit entries, are discarded without data migration or compatibility paths. The replacement uses a single `schema_v1` migration marker and one canonical full-schema snapshot.

The current development database is explicitly deleted and rebuilt once for this change. `make setup-db` remains non-destructive: it installs only an empty database or validates the current Schema V1 and refuses old, non-empty, or mismatched schemas.

This decision supersedes the Credential ownership, permission, mapping-inheritance, and executable-secret-retention clauses in ADR-0002. ADR-0002's Agent and Skill version lifecycle remains accepted. Run Snapshots continue to freeze definitions and exact secret references, but immediate ciphertext destruction means an old snapshot no longer guarantees that referenced secret material remains executable.
