# Use Thread-owned Context Evidence and rebuildable projections

Context measurement uses append-only, Thread-owned Context Evidence plus a rebuildable Context Projection rather than treating the latest Checkpoint measurement or Run Event as the complete truth. The Checkpoint remains the authority for conversation content, Context Evidence is the authority for immutable request-admission, Provider-observation, and compaction facts, and the materialized projection is only a read model. Lead evidence follows the Thread across Runs; every Sub-Agent Task execution owns an independent subject, while ToolCallControl and cumulative Run usage remain separate domains.

Context Evidence survives Run deletion and ordinary Thread Deletion together with the retained private Thread state defined by ADR-0010, and is removed only by the same explicit retention or Project-deletion boundary. It stores only scoped identifiers, digests, sizes, image measurement metadata, Token ranges, revisions, quality, reason codes, and idempotency facts; it never stores Prompt text, message or summary bodies, Tool Schema text, file content, base64 data, or Configuration Secrets. A read-side uncertainty degrades a Context Projection instead of making it unavailable, while final Provider-request admission continues to fail closed and cannot use a stale projection as authority.

This rejects reusing Run Events, which are Run-owned execution observations, and rejects using a mutable latest snapshot as the only measurement record. It accepts additional persistence and projection-repair complexity so model, Agent, Skill, MCP, policy, visual-estimator, Run-deletion, and compaction changes remain explainable without erasing already observed Token facts.

Context Evidence and its Projection Head commit atomically within the application database, but the independently committed LangGraph Checkpoint and external Provider call converge through checkpoint identities, idempotency keys, and repair. The request lifecycle records preparation, dispatch, Provider observation or failure, ambiguity, and eventual Checkpoint linkage without claiming end-to-end exactly-once execution. A crash after possible Provider success but before a durable observation remains explicitly ambiguous and never authorizes an automatic duplicate Provider call.

The Context Evidence sequence is independent from the Run Event sequence because the two histories have different ownership, retention, replay, and authorization semantics. Minimum Context Evidence required for capacity protection, Context Projection, and compaction is always recorded; the Token-usage recording preference controls cumulative usage detail and presentation rather than disabling this safety evidence.

The initial cutover replaces the Context Usage v1 contract, authority-marker endpoint, Profile compatibility proof, and frontend polling path with the Context Projection v2 REST and Thread-owned stream contracts. Gateway, Frontend, and Worker must ship together; this cutover deliberately provides no mixed-version compatibility Adapter.

One Thread-wide Context Evidence sequence orders Lead and Sub-Agent Task evidence for replay without combining their independent Context Subjects or Token values. The closed v1 evidence vocabulary is `context.window.opened.v1`, `request.prepared.v1`, `request.dispatched.v1`, `provider.observed.v1`, `provider.usage_unreported.v1`, `provider.failed.v1`, `provider.ambiguous.v1`, `checkpoint.linked.v1`, `compaction.committed.v1`, and `context.window.rebased.v1`; later changes add a new event version rather than changing an existing meaning. Context Projection recalculation is derived work and never appends evidence by itself.

Context Projection classifies model-visible material into the stable ordered lanes `system_prompt`, `agent_instructions`, `tool_definitions`, `skills`, `mcp_dynamic_tools`, `subagent_definitions`, `summarized_conversation`, `conversation`, `visual_media`, and `provider_overhead`. Every contribution belongs to exactly one lane, zero-valued lanes may be omitted from presentation, and Provider totals are not redistributed across estimated lanes to fabricate exact category values.

Context Usage is an independently authorized Thread read and is not conditional on manual-compaction capability. Manual compaction remains a separate mutation with its own capability and Run-state checks.

The Lead Context Usage surface reports the established current Context Window. Changing the input box's model selection or another preference for a future Run does not replace its Token total, capacity, category lanes, or model identity while the Thread is idle. A newly admitted Run switches the active projection to its frozen Run Snapshot; compatibility with that newly selected model is enforced at Run Admission or before its first Provider request rather than by rewriting the idle historical reading.

After Run Admission freezes a newly selected model and execution closure, the Worker measures the first final request against that frozen authority. If retained history is too large but safely compressible, it performs hierarchical automatic compaction and measures again before any Provider call; fixed material over capacity, unavailable safe cut points, or failed compaction ends the Run with `CONTEXT_CAPACITY_EXCEEDED`. The idle historical Context Projection never authorizes or prematurely rejects the new Run.

The user-facing category total is the approximate point projection and equals the sum of its visible nonzero lanes. A separately displayed last Provider input observation remains an exact historical total when available; it is never redistributed across estimated lanes. Model-visible Provider framing may enter `provider_overhead`, while engineering error allowance, the safety upper bound, and the automatic-compaction threshold remain separate indicators rather than fabricated context categories.

Browsers receive only safely projected Context Projection Heads, never raw Context Evidence. Preparation and dispatch do not publish presentation updates; a changed Head may be published after Provider observation, Checkpoint linkage, compaction, rebasing, or Sub-Agent Task settlement. REST and Thread-owned SSE merge monotonically by decimal-string `projection_seq`, and an older REST response cannot replace a newer streamed projection.

Branching creates a new Thread, Context Evidence sequence, and Context Window Generation. It copies neither source Evidence, Provider observations, nor a Projection Head; the target records one safely minimized `context.window.rebased.v1` reference to the source Thread and Checkpoint and rebuilds its first projection from the branched Checkpoint. Rollback, regeneration, message editing, compaction, and other whole-history replacements inside one Thread retain earlier Evidence, begin a new generation, append the corresponding rebase or compaction evidence, and move the Head to the replacement history.

Auxiliary model calls for summarization, title generation, input polishing, or vision bridging do not become Lead or Sub-Agent Context Subjects and do not enter their Context Usage categories. Their usage remains attributable through the RunJournal; compaction evidence records only safe digests and input/result sizes. The `summarized_conversation` lane counts only the summary text injected into a later model request, never the Token cost of generating that summary.

The v2 release has no browser API for raw Context Evidence. Internal repair, focused tests, and authorized database operations may read it; any future administrator inspection surface requires a separate field-minimization, authorization, and audit decision.

A complete bounded projection presents an approximate total such as `~134.1K`; a projection with an entirely unmeasured lane presents a lower bound such as `≥134.1K` and names the missing material. A stale Head remains visible and labelled stale, and an unknown capacity suppresses percentages without suppressing absolute Token information. Only authorization, missing Thread, or unavailable storage makes Context Usage unavailable.

Persistence uses exactly three application tables: one Thread-keyed `context_evidence_sequences` high-water mark, one Thread-owned append-only `context_evidence` ledger keyed by full private scope and sequence, and one mutable `context_projection_heads` read model per Context Subject. Evidence envelopes use stable indexed identity and lifecycle columns plus a versioned, strictly validated safe JSON payload; Projection Heads keep common selection and monotonicity fields as columns and version the lane/reason body. Evidence rejects ordinary mutation but remains deletable by the exact private-retention boundary, while a Head is freely replaceable from its authorities.

Every Provider call receives a durable identity derived from its Context Subject, Window Generation, source Checkpoint, graph step, model-call ordinal, and final request fingerprint. An idempotent replay of the same prepared call reuses its Evidence; a dispatched call without a durable outcome becomes ambiguous, an observed call without Checkpoint linkage is repaired rather than repeated, and only a Provider Adapter that proves no response was possible may classify a failed attempt as safe for policy retry. Process-local callback or LangChain run identities are never database idempotency authority.

Each Projection Head records its projector revision, projection and Evidence sequence, Checkpoint identity, and Context Window Generation. A matching Head is read directly; a credible older Head remains visible as stale while a locked repair advances it, and a missing or malformed Head is rebuilt from Checkpoint and Evidence. A rebuild is monotonic and cannot let an older projector overwrite newer state; only unavailable Checkpoint and Evidence storage prevents reconstruction.

Request-cost Adapters are model/provider facts. Visual material uses a declared dimension/detail algorithm when possible or a configured conservative per-image upper bound; without either, Context Usage remains a partial lower bound while final Provider-request admission fails closed with a visual-cost-contract error. Images never make the entire read projection unavailable.

Context attribution is positive rather than a compatibility exclusion list: each request-shaping source contributes exactly the model-visible material it owns to one stable lane, and the final guard reconciles those Contributions against the fully shaped request. Graph recursion, ToolCallControl limits, concurrency, scheduling, and compaction thresholds create no Context Contribution and do not participate in a request-content compatibility fingerprint.

Message material is canonicalized with the frozen Provider Adapter's actual wire semantics, including OpenAI Chat versus Responses, patched replay fields, vLLM reasoning, and Anthropic message formatting. Graph IDs, usage receipts, UI attribution, and other application-only message metadata never consume Context capacity or change a Provider request fingerprint. Request-only middleware transforms that are not retained in Graph state, including Input Sanitization and dangling-tool-call repair, expose pure versioned projections that the frozen Profile applies to current state before the final guard compares capacity, bytes, and message count.

Projection state is expressed through three independent axes rather than one overloaded quality enum: `basis` is `provider_confirmed`, `hybrid`, `estimated`, or `empty`; `coverage` is `complete` or `partial`; and `freshness` is `current` or `stale`. The v2 REST and SSE contracts use the same strict Context Projection payload for Lead and Sub-Agent Task subjects, carry decimal-string sequence values, and require the backend to prove that every requested Task execution belongs to the authorized Thread.

Compaction runs its model work outside the Thread lock, then revalidates the source Checkpoint and execution authority under the lock. A committed replacement Checkpoint contains a unique compaction receipt; the application transaction subsequently appends `compaction.committed` and advances the Projection Head, after which SSE may publish. If that application transaction fails, the Checkpoint receipt is the idempotent repair source; a changed source Checkpoint discards the prepared summary without writing Evidence.
